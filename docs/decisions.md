# 判断基準（Decisions）

本書は、サンプルコード削除後も判断に迷う可能性がある論点について本プロジェクトが採用する判断基準を、1項目=数行でまとめたものである。各 `D-NN` の番号は初版の ADR（Architecture Decision Record、コミット efe527b に全文あり）の番号 NN を引き継いでおり、内容はサンプルコードの有無に関わらず有効である。題名末尾の「（新規決定）」は、サンプル実装に根拠が無く旧 ADR で新たに決定した事項であることを示す。

## D-01 契約モジュールと実装モジュールの分離
- **決定**: interface のみを持つ契約モジュールと、その実装を持つ実装モジュールを常に分離する。実装クラスは専用のサフィックス（例: `Impl`）を付け、契約モジュールに実装コードを同居させない。
- **判断基準**:
  - 新しい外部リソースやドメインを追加する場合、interface は既存の契約モジュールに追記し、実装は新設する実装モジュールに置く。
  - 全 interface は共通の空マーカー interface を継承させ、契約モジュールをレイヤー横断で識別可能にする。
  - 実装を伴わない小さなユーティリティは契約モジュールに置かず、共有カーネルか実装モジュール内に留める。
- **不採用**: interface と実装を同一モジュールに同居させる構成は、実装差し替えやテストダブル注入の際に依存範囲を絞れず、依存境界をビルド設定で強制できなくなるため採用しない。

## D-02 Repository interface の配置層（古典的 DIP は不採用）
- **決定**: Repository interface は data 層側の契約モジュールに置く。domain 側の実装モジュールがそこへ依存する構成とし、interface を domain 側へ移す一般的な依存関係逆転（DIP）は採用しない。
- **判断基準**:
  - 新しい Repository interface は必ず data 層の契約モジュールに追記し、domain 側に新設しない。
  - domain 側の実装モジュールは Repository 契約モジュールに依存してよいが、Service 契約モジュールは data 層に依存させない。
- **不採用**: Repository interface を domain 側の契約モジュールに置く一般的な DIP 構成は、既存の依存グラフ・DI 登録と不整合になり大規模な再編を要するため採用しない。実装モジュール同士が直接依存する構成も、差し替えやテストダブル注入ができなくなるため採用しない。

## D-03 例外境界と Result 化の責務分離
- **決定**: Repository 層は例外を透過させる（`Result` でラップせず素の型を返すか、例外をそのまま throw する）。`Result` 化は Service 層のみが `ResultHandler` 経由で行う。
- **判断基準**:
  - Repository でエラーが起きた場合は握りつぶさずそのまま throw し、Service 層まで伝播させる。
  - 複数の Repository 呼び出しをまとめる Service メソッドは、それらを同一の `ResultHandler` ブロック内で実行し、まとめて 1 回だけ `Result` に変換する。
  - Dispatcher の切り替えはこの `ResultHandler` 内のみで行い、他の層では行わない（→ D-18）。
- **不採用**: Repository 自身が `Result` を返す構成は、Service 層での二重ラップを招くため採用しない。

## D-04 domain モデルと DTO の分離
- **決定**: domain モデルは各実装モジュールではなく共有カーネルモジュールに定義し、DTO とは構造が一致していても常に別クラスにする。
- **判断基準**:
  - 新しい外部リソースの domain モデルは共有カーネルモジュールの機能別パッケージに追加する。
  - DTO は全フィールドを nullable・デフォルト値 null で定義し、domain モデルへシリアライズ用の型やアノテーションを漏らさない。
  - 変換時の必須フィールド欠落は専用の検証関数と変換エラー型で検出する。一覧変換は 1 件ずつ失敗を許容し、他要素の変換は継続する。
- **不採用**: domain モデルを各実装モジュール配下に置く構成は、複数の契約モジュールから参照できなくなるため採用しない。DTO をそのまま domain モデルとして使い回す方式は、外部 API 側の変更が UI 層まで伝播するリスクがあるため採用しない。

## D-05 ページング組み立ての責務分離
- **決定**: Repository/Service はページングを意識せず、カーソルを含む単発取得のシグネチャのみを提供する。ページングライブラリを使った組み立てはUI 層の責務とする。
- **判断基準**:
  - 新しい一覧系 API を追加する場合、Service メソッドはページング型を返さず、カーソル引数と単発取得の形にする。
  - ページングの組み立て処理は UI 層の共有コンポーネントに置き、データ取得処理は差し込み可能な関数として受け取る。
  - 一覧の継続的な監視が要件として明示された場合のみ、別途 `Flow` 対応を検討する（単発取得の枠組みでは対応しない）。
- **不採用**: Repository/Service がページング型を直接返す構成は、契約モジュールをページングライブラリに依存させてしまい、契約モジュールを軽量に保つ方針（D-01）と衝突するため採用しない。

## D-06 テストダブルは Mokkery に統一
- **決定**: テストダブルはモックライブラリ（Mokkery）に統一する。手書きのテストダブルクラス群を共有モジュールへ集約する方式は試行後に撤回済みであり、新たに追加しない。
- **判断基準**:
  - モック対象は interface とする。具象クラスをモックする必要がある場合のみ、テスト用に open 化した上でモックする。
  - テストが呼び出し内容自体を明示的に検証したい依存は既定モードでモック化し、結果に影響しない協調オブジェクトは自動補完モードを使う。
  - 共有のテストダブルが欲しくなっても、専用の共有モジュールを新設しない。
- **不採用**: 手書きのテストダブルを共有モジュールに配置する方式は過去に試行され撤回されており、モック記述コストの低さとテストの二重メンテナンス回避の観点から再採用しない。

## D-07 依存ライブラリの安定版優先
- **決定**: 依存ライブラリの更新は安定版を対象とする。Alpha/Beta 版は原則採用せず、評価した場合は採用可否に関わらず評価記録を残す。
- **判断基準**:
  - 対象バージョンが Alpha/Beta の場合は原則見送る。ブロッカーが解消され安定版に近づいた場合のみ再評価する。
  - 対象バージョンが安定版の場合は、破壊的変更の有無を確認した上で速やかに追従する。
  - Alpha 機能を評価のみして採用しない場合も、バージョン・見送り理由・再検討条件を PR またはコミットメッセージに記録する。
- **不採用**: 積極的に Alpha/Beta 機能を採用する方針は、ビルドの不安定化やドキュメントとの乖離リスクが高いため採用しない。

## D-08 DI 定義の集約先
- **決定**: DI 定義は各機能モジュールに分散させず、アプリケーションモジュール内の 1 ファイルにレイヤー別（core / データソース / repository / service / app など）で集約する。
- **判断基準**:
  - 新しい interface から実装へのバインドは、対応するレイヤーのモジュールブロックに追記し、interface 型を明示する。
  - 新しい ViewModel はアプリケーションモジュールのブロックに登録する。
  - プラットフォームごとに実体が異なる依存は、expect/actual のプラットフォームモジュールに分離する。
- **不採用**: 各機能モジュール内に個別の DI 定義ファイルを置く構成は、登録漏れや重複バインドに気づきにくくなるため採用しない。

## D-09 モジュール分割粒度の層別基準
- **決定**: UI 層のモジュールは機能ドメイン（ユーザーが辿る一連の画面フロー）単位で分割し、data/domain 層のモジュールは外部リソース（API・永続化対象）単位で分割する。両者の粒度は非対称でよい。
- **判断基準**:
  - 新規の外部リソースと新規画面の両方が必要なら、data/domain/UI の各層でモジュールを新設する。
  - 新規の外部リソースが不要なら既存の data/domain モジュールを再利用し、UI 層のモジュールのみ新設または既存モジュールへ追記する。
  - 新規画面が既存のユーザーフローと強く関連する場合は、新しい UI モジュールを切らず既存モジュール内にパッケージを追加してもよい。
- **不採用**: 各層を常に 1:1 で新設する方式は、画面ごとに不要な data/domain モジュールを複製するため採用しない。UI 層も外部リソース単位で分割する方式は、1 つの外部リソースを複数の独立した画面フローが利用する構成を表現できないため採用しない。
## D-10 feature は domain:service と ui にのみ依存する
- **決定**: feature モジュールの依存は ui と domain:service のみとし、data 層や他モジュールの実装に直接依存しない。ViewModel のコンストラクタ注入対象も service の interface に限定する。
- **判断基準**:
  - 新規 feature モジュールの依存は ui と domain:service のみにする
  - 単純な処理に見えても Repository を直接注入せず Service を経由させる
  - Service に必要なメソッドが無い場合、feature 側で data への依存を追加せず、まず service 側にメソッドを追加する
- **不採用**: 単純な画面に限り Repository 直接注入を認める案（「単純」の基準が曖昧になり境界がなし崩しになるため却下）

## D-11 Service は外部リソース単位の interface に複数メソッドを持たせる
- **決定**: Service は外部リソースごとに 1 つの interface とし、関連する複数の操作をまとめて持たせる。1 クラス 1 メソッドの UseCase/Interactor は新設しない。
- **判断基準**:
  - 既存リソースへの新しい取得パターンは既存 Service にメソッドを追加する
  - 新しい外部リソースを追加するときのみ新しい Service interface を作る
  - 複数リソースの合成が業務ロジックとして必要なら、合成結果の概念名を持つ新しい Service を作り複数 Repository を束ねる
- **不採用**: 1 クラス 1 メソッドの UseCase/Interactor パターン（機能追加のたびに単機能クラスが増殖し DI 登録が肥大化するため却下）

## D-12 Flow を返すのは継続監視が要件のときのみ（新規決定）
- **決定**: Repository/Service の公開メソッドは、値の継続的な変化を画面が購読し続ける必要があると明示的に判断した場合のみ Flow を返す。それ以外は単発取得にする。
- **判断基準**:
  - 1 回だけ値を取得する、または起動時に 1 回だけ設定を読む場合は単発取得にする
  - 外部からのプッシュ通知や、複数画面・アプリ全体で共有する状態の継続監視が要件なら Flow（StateFlow を含む）を使う
- **不採用**: 一貫性のため全メソッドを Flow に統一する案（単発取得の呼び出し側に不要な追加処理を強いるため却下）

## D-13 キャッシュ・オフライン・認証・リトライは必要になるまで実装しない（新規決定）
- **決定**: キャッシュ・オフライン対応・認証・リトライは要件として明示されるまで実装せず、先取りの汎用化を行わない。
- **判断基準**:
  - 認証・タイムアウト・リトライは共通の HTTP クライアント設定に追加し、個々の API 呼び出し側では実装しない
  - 特定のレスポンスだけキャッシュしたい場合は、まずデータソースをリモート/ローカルに分割し Repository で束ねる
  - 複数箇所で同種のキャッシュロジックが重複し始めたら、共通ユーティリティ化をそこで検討する
- **不採用**: 提供時点であらかじめキャッシュ・認証・リトライを実装しておく案（実際の要件と合わない過剰設計になりやすいため却下）

## D-14 入力バリデーションは Service 層、レスポンス整合性検証は Converter（新規決定）
- **決定**: レスポンスの整合性検証（必須フィールドの欠落検査）は data 層の Converter で行い、ユーザー入力のビジネスルールバリデーションは domain 層の Service で行う。UI 層にバリデーションロジックを持たせない。
- **判断基準**:
  - API レスポンスの必須フィールドの検証は Converter で行う
  - ユーザー入力の空文字・文字数・フォーマット検証は Service で行い、失敗は Result の失敗として返す
  - UI 側の即時フィードバック用の軽量チェックは補助として許容するが、最終検証は必ず Service でも行う
- **不採用**: 入力バリデーションもレスポンス整合性検証と同じ仕組みで統一する案（発生源の切り分けができなくなるため却下）

## D-15 UiState は画面ごとに 1 つの data class、先頭に共通状態を持つ
- **決定**: 画面固有の UiState は共通のロード/エラー状態を先頭フィールドに持つ 1 つの immutable data class とする。ローディング/成功/失敗は画面ごとに独自の sealed class を作らず、共通の状態型を使う。
- **判断基準**:
  - 新規画面のロード中/成功/失敗表現は独自 sealed class を作らず共通の状態型を使う
  - フィールド数が肥大化したら、関連フィールドをネストした data class でグルーピングする（状態を公開するプロパティ自体は 1 つのまま維持する）
- **不採用**: 画面全体を排他的な sealed interface で表現する案（ロード中もデータを同時に扱いたい場面でブランチごとにデータを複製する必要が生じるため却下）

## D-16 画面遷移はイベントハンドラがルーターを直接呼ぶ
- **決定**: 画面遷移は Screen 層のイベントハンドラがルーターを直接・同期的に呼び、ViewModel にルーターを注入しない。軽微な一回性通知（Snackbar 等）は専用ストリームを新設せず、画面状態のフィールドに値をセットする形で表現する。
- **判断基準**:
  - 画面遷移はイベントハンドラがルーターを直接呼ぶ。ViewModel は関与しない
  - 致命的なエラーは画面全体を失敗状態にする（D-19 参照）
  - 軽微なエラーや操作結果の通知は通知用の状態にセットし、表示後に元へ戻す
- **不採用**: ViewModel が Channel/SharedFlow で一回性イベントを発行し Screen が収集する案（ViewModel がルーターを知らないという責務分離と衝突するため却下）

## D-17 テスト必須範囲は Converter/Repository実装/Service実装/ViewModel
- **決定**: Converter・Repository 実装・Service 実装・ViewModel の 4 層はテストを書く。テストダブルは単一のモックライブラリで統一する（D-06 参照）。
- **判断基準**:
  - 上記 4 層を新規追加・変更したらテストを書く。Compose UI テストは必須範囲に含めない
  - モック対象は interface とし、具象クラスをモックする必要がある場合のみテスト用に開いたクラスにする
  - 戻り値がテストの成否に影響する依存は明示的にスタブし、影響しない協調オブジェクトは自動補完モードを使う
- **不採用**: テストダブルを手書きの代替実装に全面移行し、専用の共有モジュールへ集約する案（最終的に現行方式の維持が確定したため不採用）
## D-18 Dispatcher切り替えはResultHandlerに集約する
- **決定**: Dispatcherによる`withContext`の切り替えはdomain:service層のResultHandler1箇所に集約し、Dispatcherはコンストラクタ注入で受け取る。
- **判断基準**:
  - Repository/Converter/ViewModelは`withContext`やDispatcherを直接参照せず、ResultHandlerに処理を委ねる。
  - ResultHandlerはDispatcherをデフォルト引数付きコンストラクタで受け取り、テスト時はテスト用Dispatcherを注入する。
  - 新たなI/O境界が必要になっても、極力既存のResultHandler経由に統一する。
- **不採用**: 各層が個別に`withContext`を挟む方式は、呼び出しチェーン中で不要な二重コンテキストスイッチが発生するため採用しない。

## D-19 エラー表示は4経路を使い分ける
- **決定**: エラー表示は「全画面」「一覧末尾（追加ページ失敗）」「Snackbar」「入力フィールド直下」の4経路を用途別に使い分ける。表示しない選択肢として `IgnoreThrowableHandler` もある。
- **判断基準**:
  - 画面の主データが取得できない致命的な初回ロード失敗は全画面エラー表示にする。
  - 追加ページ（2ページ目以降）のロード失敗は一覧末尾にエラーを表示するのが設計意図だが、現状は全経路が `ErrorScreenThrowableHandler` を使うため全画面表示になる（未実装、→ design-guide.md §6）。
  - 入力バリデーションエラーは対象の入力欄直下に表示し、その他の軽微・操作起因のエラーはSnackbarに載せる（D-14）。
- **不採用**: 全経路を1つ（全画面または一覧末尾）に統一する案は、読み込み済みデータを消す、または初回失敗時に空の一覧枠を表示することになるため採用しない。

## D-20 Material 2を維持しテーマ値はプレースホルダとする
- **決定**: UIフレームワークのメジャーバージョン移行は行わず、テーマの色・タイポグラフィ・シェイプの初期値はプロジェクト固有の値に差し替える前提のプレースホルダとして維持する。
- **判断基準**:
  - 新規Composableは共通テーマ抽象経由で色・タイポグラフィ・シェイプを参照し、フレームワークのテーマAPIを直接参照しない。
  - プロジェクト固有の配色・書体への差し替えは実装者の判断で行ってよいが、UIフレームワークのメジャーバージョン移行は人間の判断を仰ぐ。
- **不採用**: この時点で特定のブランドカラーを決め打ちする案は、テンプレートとしての汎用性（利用者が差し替える前提）と矛盾するため採用しない。

## D-21 表示文言はリソース化しベース言語を統一する
- **決定**: 画面に表示する固定文言はハードコードせず必ず文字列リソースへ切り出し、プロジェクト全体でベース言語を1つに統一する。
- **判断基準**:
  - 新規画面の固定文言は文字列リソースに追加し、リソース参照関数経由で表示する。
  - 動的に組み立てる文字列（ユーザー入力の埋め込みなど）はリソース化の対象外とする。
  - 多言語対応（複数ロケール分のリソース追加）は要件が明示されるまで行わない。ベース言語を1つ用意することのみを必須とする。
- **不採用**: モジュールごとに言語を自由にする案は、新規モジュールの言語選択基準が定まらずプロジェクト全体の一貫性が失われるため採用しない。

## D-22 共通コンポーネントはドメイン依存と再利用範囲で配置を判定する
- **決定**: 再利用可能なComposableの置き場所は「ドメインモデルへの依存有無」と「再利用範囲」の2軸で判定する。
- **判断基準**:
  - ドメインモデルに依存しない汎用UIプリミティブは共通UIモジュールの汎用系パッケージに置く。
  - ドメインモデルに依存し、かつ2箇所以上の画面・モジュールから再利用されるコンポーネントは共通UIモジュールのドメイン別パッケージに置く。
  - 特定の1画面でしか使わないコンポーネントはfeatureモジュール内に留め、実際に他画面での再利用が発生した時点で共通UIモジュールへ昇格させる。
- **不採用**: ドメイン依存の有無を区別せず全ての再利用可能コンポーネントを共通モジュールへ集約する案は、ドメインモデルへの依存が共通モジュール全体に広がるため採用しない。

## D-23 画面間で共有する状態はServiceに保持する（新規決定）
- **決定**: 画面間・アプリ全体で共有する状態（カート、ログイン状態、テーマ設定など）はdomain:service層に状態保持用のinterfaceを置き、実装がStateFlowを保持する。ViewModelは画面間で共有しない。
- **判断基準**:
  - 状態が1画面内でしか使われないなら通常どおりViewModelのUiStateに持たせる（本項の対象外）。
  - 複数画面・アプリ全体で状態を共有し、購読者が変化をリアルタイムに受け取る必要があるなら状態保持Serviceを置く。継続監視が要件のときのみFlowを使う原則（D-12）に従う。
  - 再起動後も状態を保持したい場合は、Service実装が永続化用のRepositoryに保存する。
- **不採用**: 複数画面で同一ViewModelインスタンスを共有する案、およびグローバルなシングルトンで状態を保持する案は、DIのスコープ管理・テスト時の差し替えができなくなるため採用しない。

## D-24 プラットフォーム固有機能はUI側にinterfaceを置きapp側で実装を注入する（新規決定）
- **決定**: UIから呼び出すプラットフォーム固有機能（共有シート、外部ブラウザ起動、クリップボードなど）はUI 層にinterfaceを置き、実装をappモジュールのプラットフォーム別ソースセットに置いてDIで注入する。
- **判断基準**:
  - プラットフォームAPIの呼び出しが必要な機能はUI 層にinterfaceを定義し、feature 層はそのinterfaceをコンストラクタ注入で使い、プラットフォーム実装クラスを直接importしない。
  - 実装はappモジュールの既存のプラットフォーム別DIモジュールに集約し、新しい宣言先を増やさない。
  - ロジックを持たない単純な値の差異（定数など）はプラットフォーム分岐の対象にせず通常のコードで分岐する。
- **不採用**: UI・feature 層に直接プラットフォーム分岐を書く案は、共通コードとプラットフォーム別コードを分離する既存規約と矛盾するため採用しない。

## D-25 複数ホストのAPIはnamed qualifierで登録する（新規決定）
- **決定**: 別ホストのAPIを追加する場合は、APIクライアント実装をbaseURL引数化し、DIコンテナのnamed qualifierでホストごとに複数登録する。
- **判断基準**:
  - 既存ホストへのエンドポイント追加は既定のAPIクライアントインスタンスをそのまま使う。
  - 別ホストのAPI追加時は、APIクライアントをbaseURL付きで新しいnamed qualifierとして追加登録し、ホスト別の設定値を定義する。
  - エラーレスポンス形式がホストごとに異なる場合は、エラー変換ロジックを差し替え可能にする（現状は未実装。導入時にAPIクライアントのコンストラクタを拡張する）。
- **不採用**: エンドポイントごとに絶対URLを直書きする案、およびホストごとに独立したHTTPクライアントを都度組み立てる案は、ベースURLとの合成挙動が未検証、または共通設定の集約が崩れ重複が生じるため採用しない。
